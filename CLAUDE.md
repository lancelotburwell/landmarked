# Landmarked: notes for future sessions

A daily architecture geography game: a static Vite + TypeScript site with a CesiumJS globe.

## Hosting and deploy
- **Live at https://landmarked.land** on Vercel (team `burwellprojects-4986`, Hobby plan). Every push to `main` auto-deploys.
- **Commits must use this repo's git identity, "Burwell Projects"** (set in the repo's `git config`, same as the Spura repo). Vercel Hobby silently skips builds from any other commit author. Don't override it with `-c user.email=…`.
- The Vercel CLI (66.6) is logged in as burwellprojects-4986 and this folder is linked (`.vercel/`, gitignored). Still deploy by `git push` (commit author rule above); use the CLI for env vars and integrations. In the desktop app the CLI installed via the Bash tool lives in its sandbox; in the user's own terminal use `npx vercel@latest …`. Marketplace terms can only be accepted by the user in an interactive terminal.
- Domain is registered at Namecheap: apex A record `216.198.79.1`, `www` CNAME to Vercel; `www.landmarked.land` 308-redirects to the apex (set up in Vercel on 2026-11-22).
- Vite `base` defaults to `/`; `vercel.json` sets cache headers.

## Layout
- `index.html` holds all the UI markup: top bar, HUD (score, question box, Results button), stage (globe, result card, pin sheet), and the intro, help and end overlays. The UI must render with no JS framework and before Cesium arrives.
- `src/main.ts`: game flow and DOM wiring. It sets `window.CESIUM_BASE_URL`, then loads `./globe` with a **dynamic import**, so Cesium stays out of the entry chunk. Never import `@cesium/*` from main.ts or game.ts, except `import type`.
- `src/game.ts`: pure logic. Loads the day (`loadDay`) or the pool (`loadPool`), practice picker, scoring, distance, per-day localStorage (`landmarked:day:<YYYY-MM-DD>` or `landmarked:day:practice`; the old single key `landmarked:day` is still read), share text. main.ts awaits the buildings at top level and starts the globe import before that, in parallel.
- `src/globe.ts`: everything Cesium. It uses `CesiumWidget`, not `Viewer`. Markers are Billboard/Label/PointPrimitive collections, and the dashed line is a `Primitive`. **Pins**: after a day is played, `showAll()` adds an HTML chip (photo and name) per building in a `.pins` layer, repositioned on every `postRender` and hidden on the far side of the globe. `onPinClick` opens the card, and `focus()` flies to the building.
- `data/buildings.json`: the building pool, one line per building, each with `clues` (a list; a reused building gets its next clue), `blurb` (a fun description for the cards), fixed `tier` and `qid`. It only grows: never delete or re-tier a building that has been scheduled; `retired: "reason"` takes one out of future days. Not bundled into the app.
- `data/schedule.json`: the record of what runs when, one line per date: `{ date, ids, clues }` (clue indexes). Days through 2026-11-23 were copied from the old in-browser picker, so nothing players saw changed.
- `public/days/<date>.json` and `public/pool.json`: generated by `scripts/export-days.mjs` (runs as `predev`/`prebuild`, so on every Vercel build), gitignored. The game fetches only today's file; if it's missing, everyone gets the same date-seeded random five from `pool.json`.
- `public/photos/<id>.jpg` + `public/photos/credits.json`: one Wikimedia Commons photo per building (640 px; CC0, PD, CC BY or CC BY-SA only) with artist, licence and page. The credit is shown on each card, as the licences require. 47 of the 50 have a photo: villa-savoye and bosco-verticale have no image on Wikidata, and lotus-temple's is GFDL only.
- `public/borders.json`: Natural Earth borders and country codes (`scripts/build-borders.mjs`).
- `public/sw.js`: service worker. App files are cached first, day files and `pool.json` network first; NASA/EOX tiles go in a bounded cache.

## Features (as of 2026-11-22)
- Intro: whole globe visible, "Five buildings a day…", a single **Play** button (Resume / See results when relevant).
- Tapping the globe is the guess (the confirm/lock-in option was removed at the user's request). Neither a bottom bar nor an on-screen imagery credit is shown; the NASA credit is in How it works.
- End screen: score and verdict, results breakdown, share, countdown + "Practice round" link, then a card per building (photo, details, description, credit). Behind it, the buildings stay pinned to the globe.
- **Share text** (user's choice): `Landmarked #22` / squares + `674/1000` / `landmarked.land`. Bare domain on purpose; no per-round points. Puzzle #1 = 2026-11-01 (`puzzleNumber`).
- **Streaks and stats** (`stats()` in game.ts, from the finished days in localStorage; practice doesn't count): the intro shows the streak ("Play today to keep it going"), and the end screen shows played, streak, best streak, average, and a 200-point score-band chart with today's band highlighted.
- **Link preview:** og/twitter meta tags in index.html and `public/og.jpg` (1200×630, the game's NASA globe + tagline, no photos). Regenerate with `node scripts/make-og.mjs http://localhost:4173/` against a running preview.
- **Analytics on Upstash Redis** (the user chose Upstash, like GeoSports): `api/event.ts` (POST), `api/rank.ts` and `api/stats.ts` are Vercel functions; the logic lives in `api/_lib.ts` behind a small `Store` interface. Only anonymous per-day totals are stored (visit, start, finish, share, practice, returning, came back from yesterday, a 10-point score histogram, country from `x-vercel-ip-country`, referring site): no player id, cookie or IP, so no consent banner. `src/track.ts` sends only on landmarked.land (or with `?track`), counts a start and a finish once per device per day (`landmarked:sent:<day>:<type>`), and never blocks the game. The end screen shows "You beat X% of today's players" once 20 or more have finished. The private dashboard is `/stats.html#<STATS_KEY>` (`STATS_KEY` env var in Vercel). The Upstash env vars are `KV_REST_API_URL`/`KV_REST_API_TOKEN` (Vercel Marketplace) or `UPSTASH_REDIS_REST_*`. Without them the API answers 503 and the game ignores it. The service worker never caches `/api/` or `stats.html`.
- **Practice:** `?practice` resumes the last practice round and `?practice=new` deals a fresh random five. Today's puzzle is never affected. The user asked for this for testing and dropped a "past days" list.

## Rules and decisions
- **No Cesium ion**: `Ion.defaultAccessToken = ''`, and every imagery provider is passed explicitly.
- Imagery: bundled NaturalEarthII, then **public-domain NASA imagery by default** (the user chose it so ads are allowed): Blue Marble NG (levels 0–8) only, brightened (gamma 1.6, brightness 1.15, saturation 1.15) because the ground atmosphere is off. Landsat WELD was dropped for speed (2026-11-22). `?imagery=eox` swaps in EOX Sentinel-2 cloudless for comparison. EOX's server is non-commercial, and its credit is shown on screen in that mode.
- **Lighting is Google Earth style:** a camera-fixed `DirectionalLight` from over the viewer's left shoulder, so there's no night side; sun and moon are hidden. The user dropped real day/night on purpose.
- Import core math types from `@cesium/core`, not `@cesium/engine`. The engine re-exports are deprecated.
- Camera: no tilt and no look; minimum zoom 250 km with NASA (closer is blur; 15 km with EOX); the home view fits the whole globe (`homeAlt()`).
- **Performance first** (user: responsive beats detailed). Render at most 1.5× CSS pixels, `msaaSamples: 1`, `showGroundAtmosphere = false` (when zooming in it switched shaders and froze the globe 1–2 s; pre-warming still left ~0.25 s, so it stays off), default tile detail (SSE 2; 3 looked blocky). Measured with `node scripts/perf.mjs <url> [js tweak]` at phone size: first tiles about 2.5 s, 5 ms frames, worst frame about 0.15 s (was 1.7–1.9 s). Re-measure after any globe change.
- **Daily schedule** (`npm run schedule`, `scripts/schedule.mjs`), chosen by the user to match how professional daily games work (an editor schedules ahead) without a server: keeps every day up to tomorrow untouched and replans the rest, 28 days ahead by default (`--days N`; `--keep` only appends, for hand edits). Per day: 2 easy, 1 medium, 2 hard; least recently used first; no return within 45 days; at least 1,500 km apart. Spread wins over the gap when the pool is small, and the most overdue slot is filled first so no building is crowded out. With 50 buildings the gap can't hold yet; the script says so. The user is fine with reuse, ideally with a new clue.
- **Runs itself:** `.github/workflows/schedule.yml` runs the scheduler every night (02:17 UTC) and, if the plan changed, commits `data/schedule.json` as Burwell Projects and pushes, which redeploys. With an unchanged pool a run only appends one day. Pull before editing the schedule locally.
- **Weekly top-up** (the agreed routine, about 35 buildings a week, 4-week buffer): write clues for the next selection ids into `data/clues/NNN-*.json`, `node scripts/build-buildings.mjs`, `node scripts/fetch-photos.mjs`, `npm run schedule`, playtest, commit and push. `export-days` warns at build time when fewer than 7 days are left.
- Scoring: 200 points within 10 km, then `200·exp(-(km-10)/800)`.
- Styling: dark theme, accent `#e3b261`, IBM Plex Mono, phone first. Don't copy GeoSports' look.

## Building pipeline (growing the pool) — IN PROGRESS
1. `node scripts/import-wikidata.mjs` → `data/candidates.json`. Holds 3,073 candidates with sitelinks, 60-day English Wikipedia views, architect, year and coordinates. Every stage checkpoints to `data/.cache/` (gitignored). Wikimedia rate-limits hard: the page views use the batched `prop=pageviews` with `continue`.
2. `node scripts/select-buildings.mjs 340` → `data/selection.json`. Filters non-buildings and stadiums; fame = 0.35·rank(sitelinks) + 0.65·rank(views); spread caps of 4 per 30 km and about 8.5% per country; tiers 37% easy / 26% medium / 37% hard. It also caches Wikipedia intros for clue writing.
3. Hand-written content goes in `data/clues/*.json` as `{ id: { name, architect, year, city, country, clue (or clues: [...]), blurb } }` or `{ id: { drop: "reason" } }`. `001-drops.json` already drops 26 picks: non-buildings plus politically charged ones (Putin's Palace, Mar-a-Lago, Yasukuni and others). An entry for an existing id appends extra clues; a drop on one retires it.
4. `node scripts/build-buildings.mjs` adds every selection entry that has a clue to `data/buildings.json` (tier from its fame rank in the selection), keeps existing buildings and tiers as they are, and flags missing fields or clues that contain the name. It prints the next ids that still need clues.
5. `node scripts/fetch-photos.mjs` adds photos (it resumes and saves as it goes).
6. `npm run schedule`.

**Next:** start the weekly batches from the 264 shortlisted buildings without clues (in fame order). The user hasn't ruled on the earlier curation ideas (cut weak "hard" picks, cap castles and cathedrals, favour modern architecture and Africa, South America and East Asia); `data/selection.json` can be browsed in the private artifact https://claude.ai/artifact/4WfScLwJ6BKAmSHqoiKYf4.

## Weekly building batch (cloud routine, Mondays)
A scheduled Claude routine follows these steps every week. Do them in order and don't skip checks.

1. Work on a new branch `claude/buildings-<YYYY-MM-DD>` from `main`. Set the commit identity first: `git config user.name "Burwell Projects"` and `git config user.email "burwell.projects@gmail.com"`.
2. `node scripts/next-batch.mjs 35` writes `data/.cache/next-batch.json`: the next 35 shortlisted buildings in the daily tier ratio, with Wikidata facts and the Wikipedia intro.
3. Decide for each one: keep, or drop with a short reason. Drop it if it is:
   - not one building (a campus, district, city, bridge, park, ruin field or statue);
   - a site of atrocity or war, or politically charged (see `data/clues/001-drops.json`);
   - in a place whose country is disputed (Jerusalem, Crimea and so on): use the reason `"HOLD: disputed location, needs owner decision"`;
   - a near-duplicate of a building already in `data/buildings.json`, or too obscure to be fair.
   Places of worship are fine.
4. Write `data/clues/<NNN>-batch-<YYYY-MM-DD>.json`, where NNN is the next free number, with one entry per id: `{ name, architect, year, city, country, clue, blurb }` or `{ drop }`.
   - **name:** the common English name. **architect:** the architect or firm; for ancient buildings use `Commissioned by …` or `Unknown builders`. **year:** completion, as a string (`"1889"`, `"c. 126 AD"`, `"1248–1880"`). **city, country:** as on a map, in short English form.
   - **clue:** 1–2 sentences, 15–35 words. Hint at form, materials, setting and one memorable story. Never name the building, its city or its country, or anything that gives the answer away alone (for example "Gaudí" or "Eiffel"). Describe places indirectly ("a harbour point", "a northern capital", "beside a red-roofed old town"). Hard ones must stay fair: give a regional hint (climate, a sea, a river, the continent's style).
   - **blurb:** 2 sentences of surprising, fun facts; names are fine. Use British spelling (colour, centre, metres), plain words and no em-dashes.
   - Use only facts from the Wikipedia intro or very well-established knowledge. If unsure, leave the fact out, and never invent numbers.
   - Match the tone of the existing ones, for example:
     - Sydney Opera House: clue "White concrete shells, all cut from one imaginary sphere, sit on a harbour point. Its architect resigned mid-build and never came back to see it finished." Blurb "The sails are covered in more than a million Swedish-made tiles that clean themselves when it rains. Utzon's winning entry was little more than a set of sketches."
     - Kunsthaus Graz (hard): clue "A blue acrylic blob with nozzle-shaped skylights, nicknamed 'the friendly alien', moored beside a red-roofed old town."
5. `node scripts/build-buildings.mjs`, then fix every problem it lists for the new buildings (missing fields, clues containing the name).
6. `node scripts/verify-coords.mjs --write` adopts Wikipedia's coordinates. Then check `git diff data/buildings.json`: only the new lines may change. Revert any change to an existing building.
7. Photos: if `python3 -c "import PIL"` fails, run `pip install pillow`. Then `node scripts/fetch-photos.mjs` (rerun it if it hits rate limits). Buildings with no usable photo are fine; list them in the PR.
8. Don't touch `data/schedule.json`: the nightly Action adds the new buildings to the schedule after the merge.
9. `npm ci && npm run build` must pass.
10. Commit the clue file, `data/buildings.json`, the new photos and `public/photos/credits.json`, then push the branch. Open a PR titled `Weekly buildings: <n> new (<date>)`. Its body has:
    - a table of name, tier, city and country, and clue;
    - the dropped and held buildings with their reasons;
    - photo gaps and anything you were unsure about.
    If you can't open a PR, push the branch and say so in your final message.

## Verify changes
- `npm run build && npx vite preview --port 4173`, then `node scripts/playtest.mjs http://localhost:4173/ <outDir>` (also try `?practice=new`). It plays a full day at phone and desktop sizes in headless Chrome, opens a pin card and saves screenshots. `vite preview` caches its file list: restart it after a rebuild.
- `npm run measure -- <url>` gives Fast-4G timings. `node scripts/compare-imagery.mjs` shows EOX and NASA side by side.
- The desktop app's built-in browser pane throttles WebGL to about 2 fps; use the Puppeteer scripts instead.
- On Windows, the Bash tool sometimes mangles heredocs containing quotes. Write edit scripts with the Write tool, then run them with node.
