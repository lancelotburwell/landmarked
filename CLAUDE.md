# Landmarked: notes for future sessions

A daily architecture geography game: a static Vite + TypeScript site with a CesiumJS globe.

## Hosting and deploy
- **Live at https://landmarked.land** on Vercel (team `burwellprojects-4986`, Hobby plan). Every push to `main` auto-deploys.
- **Commits must use this repo's git identity, "Burwell Projects"** (set in the repo's `git config`, same as the Spura repo). Vercel Hobby silently skips builds from any other commit author. Don't override it with `-c user.email=…`.
- The Vercel CLI (66.6) is logged in as burwellprojects-4986 and this folder is linked (`.vercel/`, gitignored). Still deploy by `git push` (commit author rule above); use the CLI for env vars and integrations. In the desktop app the CLI installed via the Bash tool lives in its sandbox; in the user's own terminal use `npx vercel@latest …`. Marketplace terms can only be accepted by the user in an interactive terminal.
- Domain is registered at Namecheap: apex A record `216.198.79.1`, `www` CNAME to Vercel; `www.landmarked.land` 308-redirects to the apex (set up in Vercel on 2026-11-22).
- Vite `base` defaults to `/`; `vercel.json` sets cache headers.

## Layout
- `index.html` holds all the UI markup: top bar, HUD (score, question box, Results button), stage (globe, result card, pin sheet), and the intro, help and end overlays. The UI must render with no JS framework and before Cesium arrives.
- `src/main.ts`: game flow and DOM wiring. It sets `window.CESIUM_BASE_URL`, then loads `./globe` with a **dynamic import**, so Cesium stays out of the entry chunk. Never import `@cesium/*` from main.ts or game.ts, except `import type`.
- `src/game.ts`: pure logic. Loads the day (`loadDay`, with a date-seeded random five from `loadPool` as the fallback), catch-up days (`pastDays`, `progress`), scoring, distance, per-day localStorage (`landmarked:day:<YYYY-MM-DD>`; the old single key `landmarked:day` is still read, and old `landmarked:day:practice` entries are ignored), share text. main.ts awaits the buildings at top level and starts the globe import before that, in parallel.
- `src/globe.ts`: everything Cesium. It uses `CesiumWidget`, not `Viewer`. Markers are Billboard/Label/PointPrimitive collections, and the dashed line is a `Primitive`. **Pins**: after a day is played, `showAll()` adds an HTML chip (photo and name) per building in a `.pins` layer, repositioned on every `postRender` and hidden on the far side of the globe. `onPinClick` opens the card, and `focus()` flies to the building.
- `data/buildings.json`: the building pool, one line per building, each with `clues` (a list; a building that comes back gets its next unused clue), `blurb` (a fun description for the cards), fixed `tier` and `qid`. It only grows: never delete or re-tier a building that has been scheduled; `retired: "reason"` takes one out of future days. Not bundled into the app.
- `data/schedule.json`: the record of what runs when, one line per date: `{ date, ids, clues }` (clue indexes). Days through 2026-11-23 were copied from the old in-browser picker, so nothing players saw changed.
- `public/days/<date>.json`, `public/pool.json` and `public/plan.json` (for the planner page): generated by `scripts/export-days.mjs` (runs as `predev`/`prebuild`, so on every Vercel build), gitignored. The game fetches only today's file; if it's missing, everyone gets the same date-seeded random five from `pool.json`.
- `public/photos.json` (generated by export-days, gitignored): the credits plus a content hash `v` per photo; the game and planner load `photos/<id>.jpg?v=<hash>`, so a photo replaced in the planner shows at once despite the week-long photo cache (it didn't before 2026-11-23).
- `public/photos/<id>.jpg` + `public/photos/credits.json`: one Wikimedia Commons photo per building (640 px; CC0, PD, CC BY or CC BY-SA only) with artist, licence and page. The credit is shown on each card, as the licences require. 47 of the 50 have a photo: villa-savoye and bosco-verticale have no image on Wikidata, and lotus-temple's is GFDL only.
- `public/borders.json`: Natural Earth borders and country codes (`scripts/build-borders.mjs`).
- `public/sw.js`: service worker. App files are cached first, day files and `pool.json` network first; NASA/EOX tiles go in a bounded cache.

## Features (as of 2026-11-22)
- **Difficulty isn't shown at all** (user's choice, 2026-11-23): the five rounds go from easy to hard without saying so. No tier names, no meter; points use the accent colour. The results-breakdown bars, the building flags on the globe and the pin chips' rims take the colour of their share square (🟩🟨🟧🟥, `SQUARE_COLOR` in game.ts; user's request, 2026-11-24). Tiers only drive the schedule.
- Intro: whole globe visible, "Five buildings a day…", a single **Play** button (Resume / See results when relevant).
- **Result card** (after each guess): the building photo at the top in a fixed-height box (`min(24vh, 210px)`, so the card never scrolls), whole and uncropped (`object-fit: contain`) on a blurred copy of itself, with the credit behind a faint "i" in the photo's corner (the user found a visible credit line distracting; CC BY/BY-SA still need it reachable); then points, distance, name, architect, year, place. Photos preload while the clue is read. Buildings without a photo just show the text.
- Tapping the globe is the guess (the confirm/lock-in option was removed at the user's request). Neither a bottom bar nor an on-screen imagery credit is shown; the NASA credit is in How it works.
- End screen: score and verdict, results breakdown, share, countdown, the catch-up row, a "Daily building sneak peek" row with an Instagram button (@landmarked.land; there's no X account yet, the markup has a comment for adding one), then a card per building (photo, details, description, credit). Behind it, the buildings stay pinned to the globe.
- **Share text** (user's choice): `Landmarked #22` / squares + `674/1000` / `landmarked.land`. Bare domain on purpose; no per-round points. Puzzle #1 = 2026-11-01 (`puzzleNumber`).
- **Streaks and stats** (`stats()` in game.ts, from the finished days in localStorage; catch-up days count, but not toward streaks): the intro shows the streak ("Play today to keep it going"), and the end screen shows played, streak, best streak, average, and a 200-point score-band chart with today's band highlighted.
- **Link preview:** og/twitter meta tags in index.html (title "Landmarked", description "Where in the world is this building?") and `public/og.jpg` (1200×630, just the NASA globe centred, no text; user's choice 2026-11-23; bump `?v=` in og:image when it changes). Regenerate with `node scripts/make-og.mjs http://localhost:4173/` against a running preview.
- **Analytics on Upstash Redis** (the user chose Upstash, like GeoSports): `api/event.ts` (POST), `api/rank.ts` and `api/stats.ts` are Vercel functions; the logic lives in `api/_lib.ts` behind a small `Store` interface. Only anonymous per-day totals are stored (visit, start, finish, share, practice, returning, came back from yesterday, a 10-point score histogram, country from `x-vercel-ip-country`, referring site): no player id, cookie or IP, so no consent banner. `src/track.ts` sends only on landmarked.land (or with `?track`), counts a start and a finish once per device per day (`landmarked:sent:<day>:<type>`), and never blocks the game. Once 10 or more have finished (`RANK_MIN_PLAYERS` in main.ts), the end screen shows "You beat X% of today's players" and a "Where you stand" card: today's players in five 200-point ranges (best on top), a bar per range, the share of players on the right, the player's range in gold with "YOU" (the user's design, 2026-11-23) (the user's choice on 2026-11-23 over a named leaderboard, which would need nicknames, moderation and server-checked scores). `rank()` in api/_lib.ts returns { players, beat, bands }. The private dashboard is the Statistics tab of `/planner.html#stats` (`/stats.html#<KEY>` redirects there and saves the key) (`STATS_KEY` env var in Vercel). The Upstash env vars are `KV_REST_API_URL`/`KV_REST_API_TOKEN` (Vercel Marketplace) or `UPSTASH_REDIS_REST_*`. Without them the API answers 503 and the game ignores it. The service worker never caches `/api/`, `stats.html`, `planner.html` or `plan.json`.
- **Feedback** (user's request, 2026-11-24): under the Instagram row on the end screen, "✉ Feedback straight to the creator" opens a textarea (2,000 chars). `api/feedback.ts` emails it through **Resend** (`RESEND_API_KEY`, `FEEDBACK_TO`, optional `FEEDBACK_FROM`; the default sender onboarding@resend.dev only delivers to the Resend account's own address, so verify landmarked.land in Resend to send elsewhere) with the day, score and country, and keeps a copy in Upstash (`lm:feedback`, latest 500, 10 a minute site-wide), shown in the planner's Feedback tab (`/planner.html#feedback`). No IP or player id; the privacy policy has a Feedback section. It sends from any host (unlike track.ts), so it can be tested locally.
- **Catch-up** (replaced the random practice round on 2026-11-23, user's request): `?day=<YYYY-MM-DD>` plays one of the last 5 days (`CATCH_UP`, `pastDays()` in game.ts) from the real schedule, so new players can play the days they missed and no random building from upcoming days gets dealt. The end screen shows the five days (oldest first) with each one's score, Resume or Play. A day finished through catch-up after its date is saved with `late: true`: it counts in played, average and bands but not in streaks. Catch-up rounds are counted as `practice` events on today's date; they send no visit/start/finish/share and show no rank. Old `?practice` links land on today.

## Rules and decisions
- **No Cesium ion**: `Ion.defaultAccessToken = ''`, and every imagery provider is passed explicitly.
- Imagery: bundled NaturalEarthII, then **public-domain NASA imagery by default** (the user chose it so ads are allowed): Blue Marble NG (levels 0–8) only, brightened (gamma 1.6, brightness 1.15, saturation 1.15) because the ground atmosphere is off. Landsat WELD was dropped for speed (2026-11-22). `?imagery=eox` swaps in EOX Sentinel-2 cloudless for comparison. EOX's server is non-commercial, and its credit is shown on screen in that mode.
- **Lighting is Google Earth style:** a camera-fixed `DirectionalLight` from over the viewer's left shoulder, so there's no night side; sun and moon are hidden. The user dropped real day/night on purpose.
- Import core math types from `@cesium/core`, not `@cesium/engine`. The engine re-exports are deprecated.
- Camera: no tilt and no look; the closest zoom with NASA is where one rendered pixel covers about 600 m (`closestAlt()`, about 530 km on a phone, higher on big screens; the user asked on 2026-11-23 that you can't zoom into blur, which 250 km was); 15 km with EOX. The home view fits the whole globe (`homeAlt()`).
- **Performance first** (user: responsive beats detailed). Render at most 1.5× CSS pixels, `msaaSamples: 1`, `showGroundAtmosphere = false` (when zooming in it switched shaders and froze the globe 1–2 s; pre-warming still left ~0.25 s, so it stays off), default tile detail (SSE 2; 3 looked blocky). Measured with `node scripts/perf.mjs <url> [js tweak]` at phone size: first tiles about 2.5 s, 5 ms frames, worst frame about 0.15 s (was 1.7–1.9 s). Re-measure after any globe change.
- **Planning workflow** (agreed with the user on 2026-11-23: a building puzzle and an Instagram post every day, automatic, but easy to adjust by hand). Three windows, constants in `scripts/lib/plan.mjs`:
  - **Locked**, today + 8 days (`FROZEN_DAYS`): puzzles and Instagram posts are final. They only change for a building pinned by hand.
  - **Planned**, 28 days ahead (`BUFFER_DAYS`): drafted by `npm run schedule` (`scripts/schedule.mjs`) and redrawn every night.
  - **Stock**, 21 days (`STOCK_DAYS`) of never-used buildings beyond the locked days, so a missed weekly batch never causes repeats.
- **Schedule rules:** 2 easy, 2 medium, 1 hard a day (was 2/1/2 until 2026-11-23); **never-used buildings first**, even over spread; then least recently used, no return within 180 days; at least 1,500 km apart (spread wins over the gap among repeats). **User's rule (2026-11-23): no repeats while the game is young; later, repeats are fine if the cycle is long enough not to notice, and a repeat must get a new clue.** A repeat shows a clue it has never shown; when it has none, `npm run schedule` lists it: write one under the same id in a clue file (`{ "<id>": { "clue": "…" } }`, build-buildings appends it). Options: `--days N`, `--keep` (only append), `--from <date>` (replan from a date after today, locked days included).
- **Manual changes** go in `data/pins.json` (one entry per line), which the scheduler always respects: `{ "date": "2026-12-03", "ids": ["reichstag"], "out": ["x"], "note": "…" }` runs those buildings that day and keeps the `out` ones off it (on a locked day each pinned building takes an `out` one's place, else one of the same tier, and the rest of the day stays; the swap stays even if the pin is removed later), and `{ "id": "white-house", "notBefore": "2027-01-21", "note": "…" }` keeps one out until then. A building pinned to a later date is kept out of the days before it. Instagram posts in `data/social.json` pin their building the same way. To retire a building, add `{ "<id>": { "drop": "reason" } }` to a clue file and run build-buildings, then pin a replacement on any locked day it sits on (the check flags it). For a clue rewrite on a building already in `data/buildings.json`, replace the text there too (the clue file only appends). The planner page does all of this with a click. By hand, after a change: `npm run schedule`, `node scripts/check-plan.mjs`, commit, push. If a locked day's Instagram building changes, its Metricool draft must be redone.
- **Health check:** `node scripts/check-plan.mjs` (rules in `checkPlan()` in lib/plan.mjs). ERROR (fails the nightly Action, so GitHub emails the owner): a planned day without five valid buildings, no Instagram post for today or tomorrow or a post whose building isn't in its day, under 7 days of stock, a pin problem. WARN: stock under 21 days, locked days without a post, repeats on locked days, locked buildings under 500 km apart, missing photos in the next 2 weeks.
- **Admin page** (user's request, 2026-11-23: one private site with a button per tool): `/planner.html` has tabs, Planning (`#plan`) and Statistics (`#stats`, formerly stats.html); one key unlocks both. To add a tool: a `<div class="view" id="view-<id>" hidden>` and an entry in `TABS` in its script.
- **Planner and editor** (the user asked for a private page to check and change everything, 2026-11-23): `/planner.html` (unlinked, noindex, never cached by the service worker). It reads `public/plan.json`, which `export-days` writes on every build: each planned day with photos, new or repeat, clue number, pins, the Instagram building and teaser, the closest pair, the health check, and every building in full. It holds nothing the public day files don't already, so reading it is not secret. **Editing** needs the owner's key (the `STATS_KEY`, entered once and kept in that browser): tap a building to edit its clues (in place, or add one for its next appearance; never delete, the schedule points at them), name, architect, year, city, country and blurb; fact-check against the Wikipedia intro (the text's numbers are highlighted, ones missing from the intro are listed) and mark it checked (`checked: "<date>"` in `data/buildings.json`); pick a new photo from the Wikipedia article's JPEGs or any Commons file (CC0/PD/CC BY/CC BY-SA only, saved at 640 px with its credit); swap it out of a day, keep it out until a date, or retire it. The day's Instagram building can't be swapped there. Saves go through `api/admin.ts`, which checks the key and commits to GitHub as Burwell Projects (one commit per change, "… (planner)"), so the repo stays the only source of truth; Vercel redeploys in about a minute, and pins, holds and retirements also start the schedule Action at once. It needs `GITHUB_TOKEN` in Vercel: a fine-grained token for lancelotburwell/landmarked with Contents and Actions read/write (optional `GITHUB_REPO`, `GITHUB_BRANCH`). Without it saves answer 503. To test without touching main, run the handler with `GITHUB_BRANCH` set to a throwaway branch (Node runs the .ts directly).
- **Runs itself:** `.github/workflows/schedule.yml` runs the scheduler every night (02:17 UTC), commits `data/schedule.json` as Burwell Projects if it changed and pushes (which redeploys and refreshes the planner), then runs the health check. Pull before editing the schedule locally.
- **Weekly top-up** (Saturdays, see "Weekly routine" below; the user chose weekly over daily on 2026-11-23): `next-batch.mjs` without a count sizes the batch so that after a week's use the stock is back to 21 days (10 to 60, about 15% extra for drops). It needs the cloud environment to allow `en.wikipedia.org`, `www.wikidata.org`, `query.wikidata.org`, `commons.wikimedia.org` and `upload.wikimedia.org`; on 2026-11-23 it failed because they were blocked (only the user can change that). History: on 2026-11-23 the pool grew from 50 to 138 by hand and the schedule was replanned from 2026-11-25 with fresh buildings (25–29 Nov keep their already-approved Instagram building, each with a new clue); the 50 originals had been looping every ~10 days since early November.
- Scoring: 200 points within 10 km, then `200·exp(-(km-10)/1492.7)`, GeoGuessr's world-map falloff (half at about 1,000 km). The user softened it from 800 on 2026-11-23 so non-architects can score; days played before that were scored the old way.
- Styling: dark theme, accent `#e3b261`, IBM Plex Mono, phone first. Don't copy GeoSports' look.

## Building pipeline (growing the pool) — IN PROGRESS
1. `node scripts/import-wikidata.mjs` → `data/candidates.json`. Holds 3,073 candidates with sitelinks, 60-day English Wikipedia views, architect, year and coordinates. Every stage checkpoints to `data/.cache/` (gitignored). Wikimedia rate-limits hard: the page views use the batched `prop=pageviews` with `continue`.
2. `node scripts/select-buildings.mjs 340` → `data/selection.json`. Filters non-buildings and stadiums; fame = 0.35·rank(sitelinks) + 0.65·rank(views); spread caps of 4 per 30 km and about 8.5% per country; tiers 40% easy / 40% medium / 20% hard (was 37/26/37; `data/selection.json` still holds the old tiers until it's rerun, but `build-buildings.mjs` and `next-batch.mjs` use the new split). It also caches Wikipedia intros for clue writing.
3. Hand-written content goes in `data/clues/*.json` as `{ id: { name, architect, year, city, country, clue (or clues: [...]), blurb } }` or `{ id: { drop: "reason" } }`. `001-drops.json` already drops 26 picks: non-buildings plus politically charged ones (Putin's Palace, Mar-a-Lago, Yasukuni and others). An entry for an existing id appends extra clues; a drop on one retires it.
4. `node scripts/build-buildings.mjs` adds every selection entry that has a clue to `data/buildings.json` (tier from its fame rank in the selection), keeps existing buildings and tiers as they are, and flags missing fields or clues that contain the name. It prints the next ids that still need clues.
5. `node scripts/fetch-photos.mjs` adds photos (it resumes and saves as it goes).
6. `npm run schedule`.

**Next:** the weekly batches continue from the 164 shortlisted buildings without clues (in fame order; batches 002 and 003 on 2026-11-23 added 88 and dropped 12). The shortlist runs out in about 5 months: before then, rerun `select-buildings.mjs` with a larger count. The user hasn't ruled on the earlier curation ideas (cut weak "hard" picks, cap castles and cathedrals, favour modern architecture and Africa, South America and East Asia); `data/selection.json` can be browsed in the private artifact https://claude.ai/artifact/4WfScLwJ6BKAmSHqoiKYf4.

### Part A: buildings (straight to main)
1. `git pull`. `node scripts/next-batch.mjs` (no count: it sizes the batch from the stock, 10 to 60) writes `data/.cache/next-batch.json`: the next shortlisted buildings in the daily tier ratio, with Wikidata facts and the Wikipedia intro. If Wikipedia or Wikimedia can't be reached, skip Part A and say so; never write clues from memory.
2. Decide for each one: keep, or drop with a short reason. Drop it if it is:
   - not one building (a campus, district, city, bridge, park, ruin field or statue);
   - a site of atrocity or war, or politically charged (see `data/clues/001-drops.json`);
   - in a place whose country is disputed (Jerusalem, Crimea and so on): use the reason `"HOLD: disputed location, needs owner decision"`;
   - a near-duplicate of a building already in `data/buildings.json`, or too obscure to be fair.
   Places of worship are fine.
3. Write `data/clues/<NNN>-batch-<YYYY-MM-DD>.json`, where NNN is the next free number, with one entry per id: `{ tier, name, architect, year, city, country, clue, blurb }` or `{ drop }`. Copy `tier` from `next-batch.json` (without it, build-buildings recomputes one from the fame rank, which can leave a batch with no hard buildings).
   - **name:** the common English name. **architect:** the architect or firm; for ancient buildings use `Commissioned by …` or `Unknown builders`. **year:** completion, as a string (`"1889"`, `"c. 126 AD"`, `"1248–1880"`). **city, country:** as on a map, in short English form.
   - **clue:** 1–2 sentences, 15–35 words, and above all interesting to read. Hint at form, materials, setting and one memorable story. Write to the building's tier (user's rule, 2026-11-23: difficulty is fame *and* how much the clue gives away):
     - **easy:** lead with the building's most famous feature, told in a fun way, so anyone who has seen it once gets it;
     - **medium:** a less obvious detail or story, plus a clear regional nudge (a sea, a climate, a neighbouring landmark);
     - **hard:** oblique and story-led, but always with enough place woven into the sentence to get within a few hundred km without knowing the building.
     Work the place into the story; never tack on an atlas line. Never name the building, its city or its country, or anything that gives the answer away alone (for example "Gaudí" or "Eiffel"). Describe places indirectly ("a harbour point", "a northern capital", "beside a red-roofed old town"). Hard ones must stay fair: give a regional hint (climate, a sea, a river, the continent's style).
   - **blurb:** 4–6 sentences, about 70–110 words (the user asked for this length on 2026-11-22). Cover who built it and why, what makes the design special or what to look for, and one or two surprising stories or numbers; names are fine. Use British spelling (colour, centre, metres), plain words and no em-dashes. See `data/clues/000-original-50-blurbs.json` for the tone.
   - Use only facts from the Wikipedia intro or very well-established knowledge. If unsure, leave the fact out, and never invent numbers.
   - Match the tone of the existing ones, for example:
     - Sydney Opera House: clue "White concrete shells, all cut from one imaginary sphere, sit on a harbour point. Its architect resigned mid-build and never came back to see it finished." Blurb: see its entry in `000-original-50-blurbs.json`.
     - Kunsthaus Graz (hard): clue "A blue acrylic blob with nozzle-shaped skylights, nicknamed 'the friendly alien', moored beside a red-roofed old town."
4. `node scripts/build-buildings.mjs`, then fix every problem it lists for the new buildings (missing fields, clues containing the name). Careful: once a building is in `data/buildings.json`, editing its clue in the clue file *appends* the new text as a second clue; remove the old one from `data/buildings.json` by hand.
5. `node scripts/verify-coords.mjs --write` adopts Wikipedia's coordinates (rerun on rate limits). Then check `git diff data/buildings.json`: only new lines (and appended clues) may change. Revert any other change to an existing building.
6. Photos: if `python3 -c "import PIL"` fails, run `pip install pillow`. Then `node scripts/fetch-photos.mjs` (rerun it on rate limits). Buildings with no usable photo are fine; list them in the report.
7. `npm run schedule`. For every repeat it lists without an unused clue, write a new clue (same id, `{ "clue": "…" }`, in the batch file), run build-buildings and `npm run schedule` again.
8. `node scripts/check-plan.mjs` must show no ERROR, and `npm ci && npm run build` must pass. Fix what they report; if you can't, don't push Part A and say why.
9. Commit the clue file, `data/buildings.json`, `data/schedule.json`, the new photos and `public/photos/credits.json` ("Weekly buildings: <n> new"), `git pull --rebase`, push to `main`.

### Part B: Instagram drafts for next week
10. For each date from next Monday to next Sunday that isn't in `data/social.json`, pick one building from that day in `data/schedule.json`: one that has a photo, hasn't been featured in the last 30 days, and vary the round.
11. **The photo slide must not give the building away** (user, 2026-11-25: the first crops were too wide and too recognisable). For each pick, search Commons for a high-resolution close-up (`<name> detail filew:>3000`, `<name> tiles`, `incategory:"<name>" filew:>3000`; CC0/PD/CC BY/CC BY-SA only): a texture, pattern, ceiling, corner or material, never the silhouette, the whole façade or the famous view. What the user likes most is a close-up where you really see the building's texture or a small detail (2026-11-25: the tile chevrons, honeycomb plaster and concrete blocks of 25–27 Nov). Put it in the entry as `photo: "File:…"`; `node scripts/make-social.mjs <date>` downloads it at 3840 px to `social/src/<date>.jpg` with its credit and uses that credit in the caption. Then `python3 scripts/social-grid.py <date>` and choose a crop `[x, y, width]` inside the detail: no text or inscriptions, no people, no signs naming the place. The crop must cover at least 1,080 px of the source (make-social flags anything less as soft). Without a `photo`, the game's photo is used (`node scripts/social-photos.mjs <ids>`, `W=3840`), which is rarely sharp enough to crop tightly. Write each teaser `line` (see below). Leave `first` out. Add the entries to `data/social.json`.
12. Commit only `data/social.json` ("Instagram posts <first date>–<last date>"), pull with rebase, push. The GitHub Action "Render Instagram posts" (`.github/workflows/social.yml`, it has Chrome) renders `public/social/<date>-1.jpg` and `-2.jpg` and adds the captions to `data/social-captions.json`. Wait for it: `git pull` until every new date is in `data/social-captions.json` and `https://landmarked.land/social/<date>-1.jpg` answers 200 (allow about 15 minutes; use a wait loop, not a sleep).

## Instagram reels (templates fixed 2026-11-23, posted by hand for now)
Two reel templates, chosen by the user after comparing eight formats. Neither shows the answer: the question is for the comments. Plain overlay text, no fades, no end card; the user adds music in Instagram. Both loop.
- **where** ("Where am I?"): the clue above and a big gold "Where am I?" below, on screen from the first frame. It opens on a close-up crop of the building, slowly pushing in (with a dark fade behind the clue and a soft dark glow behind the title, baked into the image on a CPU canvas: CSS and GPU-canvas gradients, blurs and shadows don't render in headless Chrome with GPU=1); at 2.2 s the photo shrinks into a circle that lands exactly on the globe and blends into it (user, 2026-11-23: no hard cut); then the globe just spins (always the same neutral spin, no zoom, no pin); from 10 s the same in reverse, so the last frame is the first.
- **who** ("Who am I?"): big gold "Who am I?" on top, the clue at the bottom, and one continuous swoop: the globe spins fast and, without pausing, slows while zooming in, coming to rest at about 3,000 km (closer is featureless) as a gold pin lands at 6.6 s; then it zooms back out speeding up the same way, exactly one full turn, so the last frame is the first. The building is never shown. Only post one after that building's day has been played (the pin gives the location away).
- `GPU=1 node scripts/make-reel.mjs <where|who> <building id>` against a running `vite preview` writes `social/reels/<id>-<template>.mp4` and `.txt` (the caption; gitignored). Options: `CROP=x,y,width` (where: the close-up, fractions of the large photo from `social-photos.mjs`, a 4:5 crop widened to 9:16; choose it on `social-grid.py`'s grid: a detail, corner or texture, no crowds, signs or inscriptions; defaults to the carousel crop), `HOOK="…"` (the caption's first line; defaults to the carousel teaser), `CLUE=n`, `AT=1,3,6.6` (only those moments, as PNGs). With the graphics card a reel takes 2–4 minutes.
- Caption (written by the script): the hook (one surprising fact from the blurb, 10–20 words, no building, architect, city or country names), then "Where am I? Guess in the comments 👇" or "Who am I? Name the building in the comments 👇" with the tier square (🟩🟨🟥), "Play at landmarked.land (link in bio)", the four general hashtags, and for "where" the photo credit with "cropped". No location tag (it shows above the video). Music: calm and neutral; never a song that matches the place (it would be a clue).
- Use easy buildings with good clues. Not automated yet.
- **Ten more formats (prototypes, 2026-11-24, not yet chosen by the user):** `GPU=1 node scripts/make-reel-formats.mjs <format>` (same preview, same Drive copy) renders `social/reels/<format>-<first id>.mp4` and `.txt`. The drawing runs in the page from `scripts/reel-page.js` (its CSS classes are `r`-prefixed: the game's own `.panel` caps widths). Each format's buildings, crops, clues and caption are in `FORMATS` at the top of the script; edit there for the next one. Formats: `zoomout` (a macro detail widens with a seconds counter, stops before the whole building), `ladder` (3 clues worth 3/2/1 points), `pins` (one clue, four numbered pins on the globe), `blueprint` (edges traced from a photo, drawn in gold on a blueprint grid), `emoji` (three emoji riddles), `lie` (two truths and a lie about a named building), `timeline` (four named buildings, oldest to newest), `stop` (the globe sweeps under a crosshair: pause when it's on the building), `pick` ("one free flight, where to?", no wrong answer, tag a friend), `speed` (five close-ups, 2 s each, comment x/5). A second batch the same day, after current Reels trends: `pixel` (depixelates in 6 levels with synthesised ticks and a ding), `silhouettes` (name 4 countries from Natural Earth outlines, bonus: a building in each), `wrongonly` ("wrong answers only", best one gets pinned), `spotdiff` (3 edits to the lower copy of a photo, 10 s timer with ticks and a buzzer), `wordsearch` ("the first city you see is your next trip"), `distance` (two named buildings and a gold arc: closest guess in km wins), `blindrank` (five places one at a time, rank before seeing the next), `realorai` (three real but unreal-looking buildings; no AI images are used, and the answer is "all real"), `thisorthat` (five quick pairs, comment your combo), `mistake` (seven pinned buildings, one in the wrong city). Formats with an `audio` list get a synthesised WAV (`soundtrack()`, ticks, ding, buzzer) muxed in; the rest are silent. Same rules: no answer on screen (it's in the .txt notes), only buildings whose day has been played, photos credited, silent by default with a suggested mood. Honest challenge wording only: no invented "only 2% get this" figures. Text stays clear of Instagram's top 170 px, bottom 430 px and the right-hand buttons.
